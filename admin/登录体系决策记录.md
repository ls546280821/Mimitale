## 一句话结论

给 Mimitale 加登录 + 客户管理后台：**客户在客户端里用邮箱验证码登录（登录即注册），
管理员（= 你自己）在后台里用账号密码登录（预置，不开放注册）**；
后台放在中国香港轻量服务器上（免备案），客户继续用自己的 API Key 客户端直连模型，
你的服务器只管账号、不碰模型内容。

**后端一共就两件事**：① 客户管理 ② 角色卡 / 世界书云同步。
**对话记录不上服务器**，由客户端自己存文件（见决策 8）。

## 决策 0：两套账号，互不相干 ⭐

**这条是结构性的，先定它，别的才排得下去。**

| | 客户（customer） | 管理员（admin） |
| --- | --- | --- |
| **是谁** | 在 Mimitale 客户端里注册使用软件的人 | **你自己**（顶多再加一两个运维） |
| **从哪来** | 客户端里自助注册 | 部署时预置写入数据库 |
| **怎么登录** | 邮箱验证码，**登录即注册** | 账号 + 密码 |
| **在哪儿登录** | Electron 客户端 | 这个 Vue 后台 |
| **调哪组接口** | `/api/client/auth/*` | `/api/admin/auth/*` |
| **数量级** | 几千 ~ 几万 | 个位数 |
| **能自己注册吗** | ✅ 能，这是设计目标 | ❌ **绝对不能** |

**为什么必须分开**（初版踩的坑）：

1. **语义不同。** "客户"是软件的使用者，是业务数据；"管理员"是系统的运维者。
   混成一张表，将来加权限、加审计、加多角色时，会发现两类人根本不该共享字段。
2. **注册策略相反。** 客户要**对外放开注册**（越方便越好）；管理员要**封闭**
   （能自助注册一个管理员的后台 = 后台被拿下的第一步）。
3. **认证方式不同。** 客户是邮箱验证码（无密码，因为客户端里输入密码很累）；
   管理员是账号密码（就你自己用，密码比验证码省事，也避免"管理员邮箱被控"这条攻击链）。
4. **数据表不该共用。** 客户表要按客户量做索引、分页、归档；管理员表就那么几行。

**落到代码上**：`admin/src/types/admin.ts` 是**这个后台**要的 6 个接口；
`admin/src/types/client.ts` 是**客户端**要的 5 个接口 —— 后台一行都不调后者。
两份文件顶部都写了这句提醒。

## 决策 1：服务器放中国香港

| | |
| --- | --- |
| 选择 | 中国香港 · 轻量应用服务器（腾讯云 / 阿里云） |
| 规格 | 2核4G + 5M 带宽 + Ubuntu 22.04（2核2G 也能跑，但要调 `-Xmx`） |
| 参考价 | 约 188 元/年（2核2G 约 99 元/年） |
| 别买 | CVM / ECS —— 贵，且用不上 |

**为什么合法**：工信部 ICP 备案管的是**中国大陆境内接入**的服务器。香港实行"一国两制"，
按"服务器所在地管辖原则"，**不需要内地 ICP 备案**。腾讯云/阿里云卖香港节点是持牌业务。

**仍然要守的底线**：内容合法（服务器放哪都管）、遵守香港本地法律、遵守《网络安全法》。

**代价（不是法律问题，是实操）**：

- 域名不能解析到内地节点（一旦回源境内就要备案）
- 国内支付接口要备案号 —— 后期接微信支付时会被卡
- 大陆访问延迟高 30~80ms，百度 SEO 降权（对 API 调用无影响）

## 决策 2：现在什么执照都不办

**关键澄清**：备案卡的是两件事，而且**分开判**——

1. 你是不是经营性的
2. 你**有没有登录、评论这类交互功能**

个人非经营性备案明确「**不支持评论、打赏、登录等交互功能**」（腾讯云备案说明口径）。
所以：**"我不收费"救不了"我要开放注册"。** 要备案就必须企业/个体户主体，跟收不收费无关；
不想办执照就别用内地节点。

### 什么时候才需要执照

| 你要做的事 | 需要什么 |
| --- | --- |
| 只做账号体系，不收费 | 什么都不用 |
| 收费，但走第三方平台收款 + 发卡密 | **还是什么都不用** |
| 站内自建支付卖会员 | 至少个体户执照 + ICP 备案 + 迁回内地 |
| 读作"有偿信息服务"（付费内容）严格合规 | **ICP 经营许可证 → 只有有限公司能办** |
| 想做平台型业务 | 有限公司 |

**ICP 经营许可证的硬门槛**（这才是"收费要注册公司"这句话的真正来源）：

- 主体必须是**内资有限公司** —— 个体工商户、个人独资企业、合伙企业**一律不予受理**
- 注册资本 ≥ 100 万（认缴，部分省要实缴）
- **3 名员工社保**
- 服务器必须在境内、域名必须过户到公司名下
- 审核 40~60 个工作日

**短信验证同样是执照门槛**：腾讯云自 **2025-09-18** 起不再支持创建个人自用资质，
签名归属主体为个人时无法完成运营商实名报备；且腾讯云已取消"网站/公众号/小程序"签名类型。
→ 想发短信，名下必须有营业执照（个体户即可，不用公司）。

> ⚠️ **个体户 ≠ 公司**。个体户能开微信/支付宝商户号、能开票、能办企业备案，
> 维护成本（建账、报税、注销）远低于公司。**能个体户就别公司。**

## 决策 3：客户端身份源用邮箱验证码，预留短信通道

> 这一段只讲**客户**怎么登录。管理员走账号密码，不参与这一节的权衡。

| 方案 | 结论 |
| --- | --- |
| **邮箱验证码** ✅ | 采用。零门槛、今天就能上、几乎零成本 |
| 邀请码 | 备选。零外部依赖，适合"发卡给谁谁用"的阶段 |
| 短信验证码 | **暂缓**。需先办个体户 → 执照 3 天 + 签名报备 7~10 工作日 |
| 微信扫码登录 | ❌ 排除。微信开放平台"网站应用"必须企业主体 + 300 元/年认证 |
| 用户名 + 密码 + 注册页 | ❌ 排除。还要额外做密码强度、找回密码 |

**为什么邮箱在桌面端体验其实更好**：Mimitale 是桌面应用，用户就坐在电脑前，
开个标签页就能收邮件。短信的优势（不用切应用）是移动端才成立的，
在电脑上反而要掏手机、解锁、找短信、念数字，更别扭。

⚠️ **如果以后上短信，这四道防护必须一起上**（缺一不可，否则一夜被刷几千块）：
前端图形验证码/滑块、同一手机号 1 分钟 1 条 / 1 小时 3 条 / 1 天 10 条、
同一 IP 每日上限、**每日发送总量熔断**。

**接口设计上，邮箱和短信是同一个形状** —— `发送验证码` + `校验验证码`。
所以现在用邮箱做，将来加短信只需后端多接一个发送通道，前端和客户端一行都不用改。

## 决策 4：合规红线 —— 服务器不碰模型 ⭐

**这是整个架构里最重要的一条。**

**"经过"指的是流经（转发），不是存储。** 只要请求或响应从你的服务器上过了一手，
哪怕一个字都不存，你也已经"经过"了。

| 做法 | 内容流经你？ | 你的身份 |
| --- | --- | --- |
| **客户端直连模型厂商**（现状） | ❌ | 账号服务提供者，**责任在模型厂商** |
| 客户端 → 你转发 → 模型厂商 | ✅ | **面向境内公众的生成式 AI 服务提供者** |
| 客户端 → 你转发 → 模型厂商，且落盘 | ✅ | 同上，**且多出内容标识/审核/数据安全义务** |

**为什么"不存"救不了"转发"**：《生成式人工智能服务管理暂行办法》管的是
"向**境内公众**提供生成文本等服务"这个行为。自己算的还是转发别家的不影响认定；
而且转发方有能力在中间拦截过滤 —— 这正是监管要的抓手。

**触发后的门槛**（比 ICP 备案高一个量级）：

- **算法备案**：线上提交，周期 **2~3 个月**
- **大模型备案 / 登记**：属地网信办线下提交，周期 **6~8 个月**
  （调用第三方已备案模型可走较轻的"大模型登记"档）
- 中央网信办正在开展**「清朗·整治 AI 应用乱象」**专项行动，
  明确把"未履行大模型备案登记义务"列为重点整治对象

**注意**：香港服务器免得了 ICP 备案，**免不了这一套** —— 因为它按"服务对象"判定，
不看服务器位置。你的用户都在境内，所以适用。

### 配套的三条执行规则

1. **用户的 API Key 永不上传**，留在本地（客户端现有的 `safeStorage` 加密即可）
2. **不做任何"聊天内容上报"的埋点** —— 日志和统计接口收下 prompt 也算经过。
   要统计就统计"今天点了几次生成"这种不含内容的数字
3. **将来做多设备同步时分开处理**：角色卡、世界书（用户自己创作）可以同步；
   **聊天记录（含模型生成内容）默认留本地**，别顺手一起传上去

### 自查方法

打开 Mimitale 的开发者工具，看 Network 面板：

- 模型请求域名是 `api.deepseek.com` 这类 → **对**
- 如果看到打向 `api.你的域名.com` → **你的服务器在中间了，要改回来**

## 决策 5：现在就买一个域名（唯一要立刻花钱的事）

把 API 地址写成 `api.你的域名.com`，而不是写 IP。

- 域名指向香港服务器**不需要备案**
- 将来迁回内地：**只改一条 DNS 解析 + 补备案，客户端一行代码都不用改**
- 反过来，如果现在把 IP 硬编码进 Mimitale，用户装了几百份之后想搬家 —— 那是灾难

## 决策 6：字典只放「真字典」，不放「假旋钮」 ⭐

星宝问：**「做后台的话，状态这些肯定是字典操控的」** —— 这句话一半对。

**判断标准只有一条：加一个新的值，需不需要改代码？**

| 放（真字典） | 不放（假旋钮） |
| --- | --- |
| 封禁原因 `ban_reason` | 客户状态 `active` / `banned` |
| 客户来源 `customer_source` | 卡密状态 `unused` / `used` / `void` |
| 额度预设 `quota_preset` | 管理员角色 `super` / `normal` |
| 卡密备注分类 `card_note` | 操作日志的动作类型 |

**为什么状态不能进字典**：后端写着 `if (status === 'banned')`，前端写着
`row.status === 'active' ? '封禁' : '解封'` —— 值本身**参与逻辑判断**。
你在字典里加一个第三态「观察中」，界面上会多出一个**选得动、但点了什么都不会发生**的
选项：后端不认识它，所有分支都掉到 else 去。**假旋钮比没旋钮更糟** ——
它让人以为系统很灵活，实际每次都得回来改代码，还多了一份没人维护的数据。

**而封禁原因不一样**：明天想加一个「刷屏广告」，在字典页加一条就完事，
封禁弹层的下拉立刻多出来，不用重新部署。这才是字典该干的活。

**落到代码**：`src/config/labels.ts` 是那些「参与逻辑判断」的枚举（含说明）；
`dict_types` / `dict_items` 两表是「真字典」。

**字典不是摆设** —— 这四处界面真的在读它：
封禁弹层的原因下拉、客户列表与详情的来源列、改额度的快捷按钮、生成卡密的备注分类。

## 决策 7：不做 RBAC，也不做菜单管理

星宝问过「菜单管理、用户管理、角色管理」这些。结论：**现在都不做，但把口子留着。**

**为什么不做**：这三样都是给**多角色协作的中大型后台**准备的。RuoYi 那套全家桶
是为了应对「100 人公司、20 个部门、5 种角色、每人可见数据不同」。

而这里的现实是：**管理员就星宝一个人，所有客户他都该看到全部。**

**RBAC 什么时候才真的需要？** 三条里任意一条成立：

- 有人**只该看部分数据**（比如客服只能看被封的号）→ 需要数据权限
- 有人**只能点某些按钮**（运营能封号、不能改额度）→ 需要按钮权限
- **菜单因人而异** → 需要菜单管理

现在一条都不成立。**为一个不存在的问题写代码，比不写更贵** —— 它会持续拖慢后面每一次改动。

**留的口子**：

- `AdminAccount.role: 'super' | 'normal'` 已预留，但**目前不生效**（它是装饰，别当成能用）
- `router.beforeEach` 已存在，将来加 `meta.roles` 检查只加一行
- 菜单已改成**数组驱动**（`src/config/menu.ts`），将来换后端下发菜单树只改数据源

**该扩的**（按真实需求排序）：操作日志 ⭐ → 客户详情 ⭐ → 卡密（收费前）→ 其它。
前两个已经做了。

## 决策 8：后端范围 = 两件事 + 一件客户端自理 ⭐

星宝 2026-10-08 划定范围，紧接着补了一句关键的：

> 我这个后端的功能：客户管理，还有他们可能需要存一些角色卡和世界书 或者对话记录，
> 用来多端共享数据，然后应该就没啥需要后台的了
>
> 对话记录应该只需要客户端可以直接保存记录文件，不需要我们这边即时给客户保存

### 范围定下来

| # | 模块 | 数据存哪 | 状态 |
| --- | --- | --- | --- |
| 1 | **客户管理**（账号 / 卡密 / 额度 / 日志 / 字典） | 服务器 | 前端已完成 |
| 2 | **角色卡 + 世界书 云同步**（多端共享） | 服务器 | 待做 |
| 3 | **对话记录** | **客户端本地文件** | 服务器不做 |

**"对话记录不上服务器"这个决定是对的**，三条理由：

- **合规**：对话记录含模型生成内容。决策 4 的规则 3 早就写了
  「聊天记录（含模型生成内容）默认留本地，别顺手一起传上去」
- **体积**：实测**一个玩得久的用户，对话记录能到 10 MB 量级**（单条消息
  正文 + 思考约 10.3 KB，10 个会话 × 100 条就是 10 MB）。
  而角色卡 + 世界书全加起来才**几百 KB**。差 20 倍。
- **价值**：多端接着聊需要的是**上下文**，不是历史全文

### ⚠️ 但第 3 件现在**做不到** —— 缺两个东西

"客户端可以直接保存记录文件"这句话，**当前代码里不成立**：

**① 现在导出的对话是 Markdown，是给人看的，不是备份**

`renderer/js/views/chatExport.js:202 exportConversation()` 导出 `.md` / `.txt`。
而一个会话对象实测有 **19 个字段**，Markdown 只留下了 `role` + `content`。
丢掉的是：

- `panel` / `panelFields` / `panelDefs` / `panelManual` —— **状态面板的全部内容**
- `summaries` —— 分段记忆摘要
- `checkpoints` —— 手动存档点
- `characterId` / `worldbookIds` / `dialoguePresetIds` —— 角色、世界书、预设的绑定
- `narrationMode` / `paceMode` / `gmMode` / `optionsSpec` —— 视角与推进设置

**导出的 .md 拿到另一台电脑，接着聊会"换了个人"** —— 状态面板空了、记忆没了、
连角色都没绑上。

**② 根本没有"导入对话"的入口**

现在有导入能力的只有三个：角色卡（`characterImport.js`）、世界书（`worldbook.js`）、
预设（`presetIO.js`）。**会话没有。**

**所以这条需求要落地，得先补：**
- 一个**完整的会话备份格式**（JSON，含全部字段，不是 Markdown）
- 一个**导入会话**的入口

### 好消息：第 3 件和第 2 件是**同一套底层**

| | 文件搬运（第 3 件） | 云同步（第 2 件） |
| --- | --- | --- |
| 序列化 | 单个会话 → JSON | 单条数据 → JSON |
| 传输 | 磁盘文件 | HTTP |
| 合并 | 用户手动决定 | 要自动判冲突 |

**格式一样，只是传输介质不同。** 所以别当两件事做 ——
先把「按条目序列化 + 导入导出」做好，云同步就是给它换一个传输层。

### 第 2 件（角色卡/世界书同步）的两个真实障碍

**障碍 1：客户端现在是"整库覆盖"写盘，直接上云会互相覆盖** ⭐ 最关键

证据都是实测的，不是推测：

- `renderer/js/data/persist.js:23` —— `saveConversations({ conversations: state.conversations, activeId })`
  存的是**全部会话**，不是"这一个会话"
- `main/ipc.js` 的三个存储通道**全是整库语义**：
  `conversations:save` / `characters:save` / `worldbooks:save`，收的都是整个数组
- `main/store.js:39 writeJsonNow()` 是"备份 + 写临时文件 + rename"的整文件替换

**后果**：A 电脑加了一张卡，B 电脑改了另一张。两边保存的都是"我这份完整角色库"，
**谁后保存谁赢，对方那张卡整份消失**。

**要改的地方** —— 存储层从"整库"拆出"按条目"：

```
characters:save          保留（本地落盘用）
characters:saveOne(id)   新增（同步用）
characters:deleteOne(id) 新增
worldbooks:saveOne(id) / worldbooks:deleteOne(id)   同理
```

**本地落盘仍然可以是整库**（本地没有并发），但**云端必须按条目** ——
否则冲突无解。

**好消息**：角色卡和世界书**都已经有 `createdAt` / `updatedAt`** 了
（实测 `1790044112251` / `1790760353257`），会话也有（`conversations.js:38`）。
做增量比对和乐观锁的底子早就有了。

**障碍 2：头像是内嵌 base64，占角色卡 90% 的体积**

实测本机 4 张卡的构成：

| 角色卡 | 整卡体积 | 其中 avatar |
| --- | --- | --- |
| 昔涟 | 25004 字节 | **22529 字节（90%）** |
| 说怪话 | 3866 字节 | 0（没头像） |
| 小王 | 665 字节 | 0 |

`avatar` 存的是 `data:image/webp;base64,...` 这种**内嵌 data URI**。

**后果**：角色卡走 JSON 同步，**同步的主要内容其实是头像图片**，
而 base64 比原始二进制还大 33%。

**做法**：头像单独上传，角色卡里只留一个 URL。
需要加文件上传接口 + 客户端"换头像"时的上传逻辑 —— 这是**新功能**，不是改造。

### 数据量测算（决定要不要为同步担心）

| 数据 | 单条实测 | 一个用户（估） |
| --- | --- | --- |
| 角色卡（不含头像） | 0.7 ~ 3.9 KB | 30 张 ≈ **70 KB** |
| 角色卡头像（另存） | 约 22 KB / 张 | 30 张 ≈ **660 KB** |
| 世界书 | 68 KB / 5 本 ≈ 13.6 KB / 本 | 20 本 ≈ **270 KB** |
| ~~对话记录~~ | 单条 10.3 KB | ~~10 MB~~ **不上服务器** |

**结论**：第 2 件是**"几百 KB ~ 1 MB / 用户"**的量级，100 个用户才 100 MB 上下。
**对服务器完全不是负担** —— `部署/服务器选购与开箱清单.md` 里 2核2G / 40G 的配置绰绰有余。

**当初"要不要买大点"的顾虑，其实全来自不要的第 3 件。**

> **一处旧口径的修订**：服务器清单第 0 节写"数据量以 MB 计" ——
> 在"对话记录不上服务器"的前提下**是对的，不用改**。
> 但如果哪天要做对话同步，那条结论立刻失效（涨到 GB 级）。

## 后端要做什么

**纯「账号中心 + 数据同步」，0 条 AI 逻辑。** 分三组接口，三组共用同一套响应约定，
但**认证入口、数据表、注册策略全都分开**（见决策 0）。

响应统一 `{ code, message, data }`，`code === 0` 为成功；
认证走 `Authorization: Bearer <token>`，认证失败返回 HTTP 401。

#### 两条后端必须照抄的规则

1. **操作日志只由后端写入**，且**不开任何写入接口**。
   封禁 / 解封 / 改额度 / 生成卡密 / 作废卡密 / 改动字典，都在同一个事务里顺手写一条日志。
   日志如果靠前端上报，它记录的只是"前端愿意上报的部分"，出事时没有证据价值。
   另外：**值没变就不写** —— 重复提交同一个额度不该刷出噪音。
2. **字典只收"加新值不需要改代码"的枚举**。见下面「决策 6」。

### 数据表

**第一组：账号与运营**（四张，别合并）

**`customers`** —— 客户表，会长大
`id` · `email`（唯一，登录标识）· `nickname` · `status`（active/banned）·
`ban_reason`（封禁原因，字典值，解封时清空）· `quota`（-1 = 不限量）·
`invite_code`（可为 null）· `created_at` · `last_login_at`

**`admins`** —— 管理员表，就几行
`id` · `username`（唯一）· `password_hash`（**必须加盐哈希，别存明文**）·
`nickname` · `role`（super/normal，现在用不上，留着）· `last_login_at`

**`operation_logs`** —— 操作日志，**只增不改不删**
`id` · `admin_id` · `admin_name`（冗余存一份，管理员改名了历史日志也不变）·
`action` · `target_type` · `target_id` · `target_name`（同上，冗余）·
`detail` · `ip` · `created_at`

**`invite_cards`** —— 卡密
`id` · `code`（唯一）· `note`（字典值）· `status`（unused/used/void）·
`used_by_customer_id` · `created_at` · `used_at` · `expire_at`（null = 永久）

**`dict_types`** / **`dict_items`** —— 字典
types: `code`（唯一，主键式）· `name` · `remark` · `created_at`
items: `id` · `type_code` · `label` · `value` · `sort` · `enabled` · `remark`

**第二组：用户数据同步**（决策 8 的第 2 件，先占位）

**`user_characters`** —— 用户的角色卡
`customer_id` · `char_id`（客户端生成的那个 id，实测形如 `cmuc21oqk-0`）·
`data`（整张卡的 JSON）· `updated_at`（客户端给的）· `deleted_at`（墓碑）
**主键 `(customer_id, char_id)`**

**`user_worldbooks`** —— 用户的世界书，结构同上（用 `book_id`）

**`user_files`** —— 头像等附件
`id` · `customer_id` · `path` · `mime` · `size` · `created_at`

> **为什么 `data` 直接存 JSON，不给角色卡拆列**：角色卡现在 22 个字段、以后还会加。
> 拆列意味着**每加一个字段就要改表 + 改接口**，而服务器**不需要查角色卡内部**
> —— 不会有人要"按角色名搜别人的卡"。服务器对这个数据的角色就是**网盘**：
> 存、取、按时间比对。存 JSON 就够了。

> **`deleted_at` 为什么必须有（同步的经典坑）**：不做墓碑的话 ——
> A 电脑删了一张卡 → 服务器删了 → B 电脑下次同步发现"我这有、服务器没有"，
> **会把它当成"我这边新增的"重新传上去**。卡就复活了，而且**永远删不掉**。
> 墓碑就是"这块地方空着，别再传回来了"。

> **不要加外键、不要合并**。`customers` 和 `admins` 之间唯一的关系是"管理员管理客户"，
> 那是业务关系，不是数据依赖 —— 删掉一个管理员不该影响任何客户。
> `operation_logs` 里的 `admin_name` / `target_name` 是**故意冗余**的：
> 日志要能反映"当时发生了什么"，客户改了昵称之后老日志不该跟着变。

### 唯一的外部依赖

发邮件服务（SMTP / 阿里云邮件推送 / 腾讯云 SES），**只给客户端的验证码用**。
管理后台走账号密码，**不依赖邮件**。**仅此一个外部依赖。**

### 技术选型

- 后端框架**不建议用若依**：它是"企业内部 OA"思路（账号由管理员创建、**没有自主注册**），
  跟"客户要对外放开注册"的方向正好相反，14 个子系统只有 1 个用得上。
  （有意思的是：若依原本那套"管理员建号"的思路，**用在管理员表上反而是对的**，
  只是它管不了客户。）
- 若要现成脚手架，看 **ContiNew Admin**（Spring Boot 3 + Sa-Token + MyBatis-Plus /
  Vue3 + TS + Vite5 + Arco Design，Apache-2.0）—— 但注意它**同样没有客户自主注册**，得自己补。
- 更实在的判断：**这个需求根本不需要中后台全家桶**，几百行的账号中心就够。
